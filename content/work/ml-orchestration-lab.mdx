This lab is where I learn how ML platforms run GPU work: queues and quota, gang
scheduling, preemption, what happens to a run when its pod is taken away, and
how an operator can tell what any of it is doing. It runs on the platform
described in [The Homelab](/work/the-homelab), and it has one GPU, a 16 GB RTX
5060 Ti. The lab's design record says outright that it is built for patterns
that matter at scale, such as many GPUs, mixed node types and fault injection,
and that it is oversized for the one card it has.

Most of the work falls in two stretches, with smaller pieces between them. At
the end of June, while the lab briefly had a second GPU, a series of training
runs measured data-parallel training across two mismatched cards, scheduled by
Volcano. A Slurm cluster went in beside the Kubernetes stack in mid-July. From
late September, Kueue and Argo Workflows went in around the remaining card,
along with a pipeline that submits experiments to it, a record of how every run
ended, and a tracker that shows them.

## One card, many claimants

The card is a consumer Blackwell part. It has no MIG partitioning and no vGPU,
so it can't be split in hardware. The cluster's GPU node is an unprivileged LXC
container on the tower, which lets the card be shared with the tower's other
containers. A VM would need the card passed through, and passthrough gives the
whole card to one VM.

The NVIDIA device plugin time-slices the card into eight `nvidia.com/gpu`
units, and a pod may hold at most one. Time-slicing shares compute and nothing
else. Every slice sees all 16 GB, and a workload that runs past the card's
memory gets an out-of-memory error at run time, not a refusal at admission. The
slice count went from four to eight at the start of October, so that each model
could run as its own Deployment with its own slice. The count is coupled to
Kueue's quota, and the two always change together.

These are the claimants:

- **Resident models**, always on: an embedding server, speech-to-text,
  text-to-speech and object detection. Each holds a slice.
- **Two on-demand language models**, a 7B that also serves LoRA adapters and a
  12B. Both are scaled to zero by default, and at most one runs at a time.
- **A GPU notebook**, also scaled to zero until someone needs it.
- **Experiments and benchmarks**, submitted as Argo workflow steps.
- **Fine-tuning**, which takes all of the general queue's free quota while it
  runs.
- **GPU CI**, build steps that run on the card.

There is no autoscaler. An on-demand model sits at zero replicas in git, and an
operator's `kubectl scale` sticks because Argo CD is told to ignore the replica
count on those Deployments.

### How the scheduler became the arbiter

Until late September, GPU work ran in five containers that the card is
bind-mounted into, none of them owned by a scheduler. A shell script called the
lease arbitrated inside only one of them, the inference container. It stopped
the language model before a heavy job and restarted it afterwards, and it knew
two services by name. Other model servers in the same container sat outside its
view, one of them holding 12.4 GB while resident, and nothing in the other four
containers was under it at all. The lease would leave such a server running,
report the card free, and the heavy job would run out of memory. The lease
gained a registry of its tenants, then a check that reads which processes
actually hold GPU memory, through their cgroups, instead of trusting service
names.

The ruling that replaced it said the lease existed only because of that
topology, and the fix was to remove the topology. Every GPU consumer would move
into Kubernetes, arbitrated by priority classes, Kueue's quota and Volcano's
gangs. The models moved into the cluster as
Deployments over the following week. The lease's registry has been empty since
the end of September, and asking it for the card now fails with a message that
names the Kueue path instead. The lease is still installed, the card is still
mounted into the tower's other containers, and the Slurm compute node described
below still has it. Removing those mounts is the last step, and it waits on
Slurm moving into the cluster.

### A priority ladder

Every GPU tenant carries a PriorityClass. The ladder, minus one superseded
class, reads:

| Class                     | Value | Who                                          |
| ------------------------- | ----- | -------------------------------------------- |
| `registry-critical`       | 20000 | the in-cluster container registry            |
| `gpu-serving-resident`    | 15000 | the always-on models                         |
| `gpu-training`            | 9000  | training Jobs, the default for GPU steps     |
| `gpu-serving-preemptible` | 5000  | the on-demand language models, the notebook  |
| `tower-service`           | 1000  | other services on the GPU node               |
| `gpu-batch`               | 500   | benchmarks, CI, experiments submitted low    |

The registry sits at the top on purpose. Tenant images are pulled through it,
and evicting it to admit a GPU pod would strand that pod's own image pull. The
values are sparse so classes can be inserted later. `gpu-batch` also carries
`preemptionPolicy: Never`, which stops kube-scheduler from preempting anything
to place it. That setting governs kube-scheduler only. Kueue compares the
priority value, and a drill showed a training Job evicting a `gpu-batch` Job
through Kueue, with the victim readmitted afterwards. Priority also has no say
in the kubelet's own evictions when a node runs short of memory.

The ladder's ceiling was proven in early September, before the GPU tiers
existed, with a drill and a negative control staged on memory. A pod in an
older burst class preempted a drill victim at priority −1000. The same pod,
aimed at a `registry-critical` victim, got `Preemption is not helpful for
scheduling`.

## Kueue decides whether, Volcano decides where

Two schedulers run here, at different layers, and a design note in the GitOps
repo draws the line between them. Kueue is the admission and quota layer. It
never places a pod on a node. It holds a pod's scheduling gate until the pod's
priority, its queue and that queue's quota say it may proceed, then releases it
to whichever scheduler the pod names. Volcano is a placement layer, and the
only one of the two that understands that N pods must land together.

<Figure num="Fig. 1" caption="A GPU pod's path. In the workflow namespace, Kyverno checks a GPU step came from an approved template. Kueue holds the pod until quota allows. Then kube-scheduler places a single pod, and Volcano places a gang all at once or not at all.">
  <GpuAdmissionFlow />
</Figure>

Gangs need both layers. Kueue's pod integration admits pods one at a time,
which could admit half of a gang that Volcano would then wait on forever.
Kueue's pod-group labels close that gap. When each pod carries a group name and
a total count equal to Volcano's `minAvailable`, Kueue builds no Workload until
all N pods exist, then ungates them together. Volcano then binds all N or none.
The design note's summary is two gang guarantees, one per layer: quota
admission in Kueue and node placement in Volcano. A pod can clear Kueue's quota
and still have nowhere to land, and it can have a node waiting while quota
holds it back. The composition was checked against Kueue's source at the
installed version, and a two-pod gang ran both pods together on the cluster.

Volcano runs its enqueue, allocate, backfill, preempt and reclaim actions. Its
preempt action only evicts the slack a job holds above its gang's
`minAvailable`, never the gang's floor, and it finds no victims at all unless
the gang and fair-share plugins are marked preemptable in the scheduler's
config. On the gang template, any evicted pod restarts the whole Volcano Job.

One priority ordering has two readers. Volcano's preempt and reclaim actions
and Kueue's preemption compare the same PriorityClass value, but they act on
different objects. Volcano evicts pods at placement. Kueue evicts whole
Workloads at the quota level, sometimes before a pod even exists. The case
where both act on one gang has not been exercised.

Volcano's install file records the trade-off of running it. A second scheduler
is more to operate, and two schedulers can race to bind the same resource,
though neither problem bites on a single GPU node. The lighter alternative was the coscheduling plugin. Volcano won on its job
launcher, which hands each pod the peer addresses that Gloo training needs to
rendezvous, and on its fuller set of preemption and fair-share actions.

The June gang and preemption demos ran across two GPU nodes. They were rebuilt
for one node in early October. With one of the two slices a gang needed free,
no gang pod started, and the gang waited for both. Freeing a second
slice let both pods start together. In the preemption demo, a high-priority job
evicted one of three low-priority pods. The rerun also found that the embedding
model permanently holds a slice, so the demos now size their filler jobs from
the free count.

Kueue went in while the lab has a single GPU node, so that a second node, when
it comes, can be debugged on its own. It manages pods, Jobs, Deployments and
StatefulSets in four namespaces: research, workflows, serving and CI. A
portability rule keeps the experiments out of all of this. Scheduler objects
appear only in the platform's GitOps repo. A study never names a queue, a gang
or a GPU resource, and a test in the experiment repo fails the build if one
does. The one exception is that repo's CI configuration, which has to request a
GPU for the GPU test lane. Swapping a scheduler is meant to be a platform
change that touches no study.

## The queues

<Figure num="Fig. 2" caption="The quota shape. Two ClusterQueues share a cohort. The general queue owns all eight slices and lends one. The large-model queue owns none and may borrow one, so at most one language model runs.">
  <GpuQueueTree />
</Figure>

The quota shape is small. Two ClusterQueues share a cohort, so unused quota can
be lent between them. The general queue owns all eight slices and lends one.
The large-model queue owns none and may borrow one. Both language models sit
behind that second queue, which caps them at one running at a time. A nominal
quota of one would have let the cohort admit nine units against eight real
ones. Five LocalQueues feed the two: resident serving, the on-demand models,
research, workflow steps, and CI.

Before this, a guard in each model's systemd unit refused to start one
language model while the other ran. That rule is now a quota.

Each ClusterQueue also covers CPU and memory, because Kueue won't admit a
workload that requests a resource its queue doesn't cover. Those quotas are
tight. Committed quota plus everything outside Kueue comes to about 97% of the
GPU node's CPU and 99% of its memory.

A drill at the end of September, when the card still had four slices, checked
the cap. With the 7B running, scaling up the 12B left it gated with
`insufficient unused quota for nvidia.com/gpu`, and the card held exactly one
large engine. A training Job of three one-slice pods at higher priority then
reclaimed the borrowed slice. Kueue preempted the 7B with the reason
`InCohortReclamation`, the Job ran on a card with no language model loaded, and
the model was serving again about two minutes after the Job finished. Kueue
readmitted the model before the Job reported complete, because quota frees as
each of the Job's pods finishes.

Since late September, fine-tuning has reserved the card through Kueue. Until
early October the reservation was a placeholder, and the training itself ran in
a container outside the cluster. A pod can't hold more than one slice, so the
reservation can't be one pod asking for the whole card. The trainer now runs on
one slice beside a ballast Job that claims the rest of the general queue's free
quota, which reclaims the slice the 7B borrows by the same
`InCohortReclamation` path. The script refuses to start while the 12B is up.

The queues' resource flavor is pinned to the GPU node by hostname as well as by
label. The second GPU node from June carried the same label and has been
offline since, and a workload sent there would sit Pending in a way that looks
exactly like a quota problem.

Slices count shares of compute. Memory is the scarcer resource, and the queues
now carry a VRAM resource too. A small CronJob advertises 15,888 MiB on the
node every ten minutes, the card's 16,311 MiB less what the driver reserves.
The large-model queue may borrow up to 12,400 MiB of it, one language model's
worth at its configured memory share, and the remaining 3,488 MiB is
guaranteed to the general queue. That accounting is inert today. Every tenant
still declares zero, the CI check on declarations only warns, and nothing caps
a process at what it declared. In practice, memory is protected by each vLLM
server's memory-utilization setting and its refusal to start when too little
memory is free.

Two alternatives were weighed. Dynamic Resource Allocation with consumable
capacity is the target. It is alpha and off by default in the installed
Kubernetes and Kueue and in NVIDIA's DRA driver. That driver isn't installed,
and it can't run beside the standard device plugin. HAMi was rejected. Its device plugin replaces
NVIDIA's, its scheduler conflicts with Volcano gangs on a single GPU node, and
it needs privileges an unprivileged container can't grant.

## Where a GPU step waits

A GPU step can be held in several places, and each one reports it in its own
vocabulary:

| Held by               | What the operator sees                                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Argo's GPU lock       | The workflow is Pending on `Waiting for workflows/ConfigMap/gpu-semaphore/gpu lock`. No pod exists yet, so Kueue has nothing to see.                                          |
| Kueue's gate          | The pod is Pending with Kueue's scheduling gates on it. Its Workload shows `QuotaReserved=False` and a reason such as `insufficient unused quota for nvidia.com/gpu`.          |
| Kyverno               | The pod is never created. The denial names the missing queue label or template annotation.                                                                                    |
| The kubelet           | A pod that asked for more than one slice clears Kueue and then fails on the node with `UnexpectedAdmissionError`.                                                             |
| A node that isn't there | The pod sits Pending, looking like a quota wait. The flavor's hostname pin keeps workloads off the offline node.                                                            |

An alert fires when a GPU workload has been inadmissible in Kueue for fifteen
minutes.

The operator commands follow the same model. Starting a language model while
the other one serves doesn't refuse any more. The command scales the Deployment
to one anyway, Kueue gates the pod, and the command waits, exiting with its own
code if it times out still queued. Its status output prints the pod's Workload,
the reason it isn't admitted, its position in the queue and the ClusterQueue's
usage.

The drills are scripts kept in the GitOps repo: preemption, quota and
borrowing, the GPU step template, the webhook scope, alert firing, a real node
drain, the benchmark reaper and the Volcano demos. Each refuses to start, with
a reason, when the cluster isn't in the state it expects, and most have a
read-only preflight mode. The drain drill uncordons the
node on every exit path.

## Submitting GPU work

GPU steps in Argo Workflows go through two approved templates. The single-GPU
step template sets the queue label, the priority, a deadline of
900 seconds by default, memory of 2 GiB requested and 4 GiB allowed, and a
retry policy that retries on `OnError` only. A caller can pass a Secret, a
volume, more memory and a longer deadline. The retry policy covers a pod
deleted out from under the step, which is what preemption does. In a test,
deleting a running step's pod was recorded as an error and retried in three
out of three runs. A failure in the study's own code isn't retried.

The gang template creates a Volcano Job from an Argo resource step, with
`minAvailable` and the replica count taken from the same parameter, and with
Kueue's pod-group labels on each pod. It sets no retry policy on purpose:
re-running the create would collide with the first Volcano Job or quietly make a
second one.

In the workflow namespace, Kyverno enforces two rules on any pod that requests
a GPU. It must carry a Kueue queue label, and it must carry the annotation the
templates stamp on it. The policy's comment explains the second rule: a
hand-written pod that copies the queue label alone is still rejected. GPU
workloads in the research and serving namespaces carry their queue labels by
convention.

Single-GPU steps are serialized by Argo's own semaphore, set to one. Kueue
would happily admit a second one-slice step while slices are free, and it has
no way to make one workflow's step wait for another's. The gang template sits
outside that lock on purpose.

A benchmark workflow brings up a small model server in the research namespace,
sends it requests, and tears it down in an exit handler. Review found where its
lock has to sit: a lock on a template releases when that step finishes, so the
benchmark holds its lock for the whole workflow, cleanup included. During the
control-plane incident below, the exit handler's own pod couldn't be created,
which left a benchmark server orphaned and holding about 5 GB of the card.
Deleting the Workflow object doesn't run the exit handler at all either. A
reaper CronJob now deletes benchmark Deployments whose time to live
has passed. It requests no GPU and carries no queue label, so it still works
when Kueue is the thing that's down. A drill deleted a running benchmark's
Workflow and watched the reaper collect what it left.

Workflows are archived to Postgres for fourteen days, and their logs and
artifacts go to Garage under a matching lifecycle rule. Finished pods are
collected five minutes after a workflow completes, so log reads aren't raced.
The experiment repo's own database is the durable record of results, so Argo
keeps a finished workflow object for an hour after success and a day after
failure. A CI check requires each of these retention settings to carry a
written reason.

## An experiment, end to end

The experiment pipeline lives in its own repository. It began as the harness
for a research program on language-model internals, which is now dormant, and
in late September it was re-scoped as a general lab for running arbitrary
experiments on the cluster.

<Figure num="Fig. 3" caption="An experiment from submit to record. The platform's GPU step template names the queue, so the study never has to. The run row and the telemetry key back to the pod, and the artifacts key to the row.">
  <ExperimentFlow />
</Figure>

**A study** is an importable module with a `main(spec)` function, and a spec is
one JSON object. A sweep is a list of specs. Argo runs everything on the
cluster, and an in-process runner covers CPU development and tests. The repo
has no Slurm or Volcano adapter, since under the portability rule those are
platform surfaces.

**The images.** CI publishes the lab image from `main`. PyTorch's CUDA wheels
carry the runtime, so there is no CUDA base image, and the image is about 4.4
GB compressed. A smaller image without PyTorch carries the tracker's API and
web app, and a third adds the notebook environment.

**Submission.** The CLI posts an Argo Workflow straight to the Kubernetes API,
referencing a cell template for one spec or a sweep template for several. It
authenticates as a narrowly scoped service account. That account can create,
read and stop workflows, read pods and their logs, and list Kueue's Workloads.
It can't read Secrets, list events, write Kueue's objects or reach the serving
namespace. A wrapper hands the credentials to the CLI through pipes, so they
never touch disk. The templates live in the experiment repo, and the GitOps repo
syncs them into the cluster pinned to a commit. The cell template's GPU branch
calls the platform's GPU step template, which is how the experiment repo avoids
ever naming a queue. The spec reaches the container base64-encoded, so a spec
can't inject into the shell command. The CLI also records what it sent as a
submission row. If that write fails after Argo accepted the workflow, the
workflow keeps running, and the command prints the workflow's name and the
error and exits non-zero.

**The record.** Each run opens a row in Postgres that records where it ran
(namespace, workflow, pod, retry and image), the commit its code came from, and
a hash of its config. It also records a manifest of the environment: the
driver, the newest CUDA version that driver supports, the GPU's identity, power
limit and clocks, the CPU model and a hash of its flags, and the threading
settings. All of that is hashed. The memory free on the card at open, and which
host and pod the run landed on, are recorded and kept out of the hash. The free
memory reading doubles as a measure of the neighbours. At one open, other pods
were using 3.47 GB of the card.

An idempotency key covers the config, a fingerprint of the source of the
packages that produce results, the model, the dataset, the condition and the
seed. A partial unique index allows at most one succeeded row per key. A run
whose key already has a success opens as skipped unless it's forced, and
forcing it marks the old row superseded. Until early October, a study's own
hyperparameters weren't part of the config, so two specs that differed only in,
say, learning rate shared a key. They are now. A config without them hashes
byte for byte as before, which was checked against every existing row, so no
key already on record changed. Two identical specs in one sweep still share a
key, and refusing such a sweep at submit isn't built.

Artifacts go to Garage under the SHA-256 of their bytes. The write order is
put, then insert, so the worst a crash can leave is an orphaned blob, which a
garbage-collection command deletes after a day's grace.

**Checkpoints.** A run can store a checkpoint as a derived artifact and, on a
retry, walk back through the attempts it replaces to the nearest one that wrote
a checkpoint. The execution contract lists what a checkpoint must carry for a
bit-for-bit resume, including the optimizer state, both random number
generators, the data cursor and the epoch order. The resume tests drop each of
those in turn and expect the resume to stop matching. They run in CI, and a
live resume on the cluster hasn't been run yet. A job that reclaims
checkpoints no longer needed, and the blobs they leave behind, is scheduled
daily in dry-run mode.

**Model weights** come from a cache volume on the GPU node, filled by a Job and
mounted by the cell template since early October.

## When a run ends

Four ways of taking a pod away arrive the same way. Kueue preemption, a node
drain, a retry of an infrastructure error and a cancel all send SIGTERM, then
SIGKILL after the thirty-second grace period. The signal doesn't say which one
it was.

<Figure num="Fig. 4" caption="How a run's row gets its final status. SIGTERM, whatever sent it, ends in one compare-and-set, and a cancel mark written beforehand decides between interrupted and cancelled. What the process can't report, the reaper finds.">
  <RunEndingsFlow />
</Figure>

The signal handler records the signal and raises `SystemExit(143)`. It writes
nothing itself, so it can't deadlock against a database lock the interrupted
code was holding. The run's context manager closes the row on the way out with
a compare-and-set on `running`, under a row lock: `cancelled` if a cancel was
requested first, `interrupted` if not. `failed` keeps its meaning, that the
code raised or the process died, so a preemption that closes its row cleanly
is never counted as a failure.

A cancel writes its mark on every running row of the workflow before it asks
Argo to stop the workflow, and it withdraws the marks if that request fails. A
live cancel closed its row 2.1 seconds after the request, and Argo didn't retry
the stopped step. Argo marks a stopped workflow `Failed`, so the row, not the
workflow's phase, is what says it was a cancel.

A drill in early October preempted a real cell. A low-priority cell held a
little GPU memory, and a ballast Job at training priority, sized from the live
queue to need one more slice than was free, came in behind it.

<Figure num="Fig. 5" caption="The preemption drill, one trial. Rows are in order, not to scale. The run row closed before the preemptor had its quota, and the retry waited in Kueue for about two and a half minutes.">
  <PreemptionTimelineSvg />
</Figure>

The cell's row closed 58 ms after the preemptor's Workload appeared, 5 ms after
the signal reached the pod. The drill showed that Kueue frees quota when it
evicts, before the evicted pod has exited. It also showed that the requeue is
Argo's. A plain pod can't be suspended, so Kueue deletes it, and Argo's retry
policy makes a new one. That retry waited at Kueue's gate for about two and a
half minutes, holding Argo's GPU lock while it waited. An interrupted attempt
keeps whatever it wrote, so a reader that counts results without filtering on
status counts that cell twice.

One trial can't rule out a race the execution contract records. In the drill,
Kueue's finalizer kept the deleted pod's object around for a few seconds after
its container exited. If Argo reads the pod in that window, it sees `Failed`
with exit code 143, and `OnError` won't retry it. A kubelet eviction
under node memory pressure also leaves a failed pod that wouldn't be retried.
That path comes from reading Argo's source and hasn't been tested.

A pod killed outright can't close its own row, and neither can study code that
swallows the exit or an unwind that outlasts the grace period. A reaper runs
every ten minutes as an Argo CronWorkflow and fails rows that have been silent
for two hours. Heartbeats aren't periodic. A study beats once per unit of work,
so the threshold comes from how long a GPU step is expected to live instead.
The default deadline is 900 seconds, callers have raised it to an hour, and two
hours is twice that. A study that needs longer has to raise the reaper's
threshold too. A false reap costs more than a slow one. With one success allowed per
key, a wrongly failed row could let a duplicate of a cell that's still running
start.

The stalled-run alert used to fire after fifteen minutes without a heartbeat,
which the contract never promised. It now fires at two hours and fifteen
minutes, and its title says the reaper may be down, since a row that old means
the reaper's sweep hasn't run.

Kubernetes events reach SigNoz as logs through the cluster's collector.
Kueue's own record of a preemption is an event on the Workload that lives for
an hour, and the Workload is garbage-collected with its pod, so the run row is
the record that lasts.

Nothing publishes run lifecycle events yet. The homelab already has an event
log, a transactional outbox from Postgres into Redpanda. The design slot is to
write run events (opened, gone quiet, finished, failed) to an outbox table in
the same transactions that change the run row, and to have Argo Events start an
analysis or debrief workflow when a study finishes. Neither half is built.

## The tracker

Until early October, the only record of a cell was its run row, and a cell
whose pod never started had no row. That covers an unschedulable pod, an image
that failed to pull, or a process killed before it opened its run. Once Argo's
archive aged the workflow out two weeks later, nothing showed it had been
attempted, and planned work had no record anywhere.

<Figure num="Fig. 6" caption="What the tracker reads, and from where. Results come only from the experiment database, and only the study pod writes them. Workflow phase is read live from Argo, then from Argo's archive once the live object is gone.">
  <TrackerFlow />
</Figure>

A `planning` schema now sits beside the run records. A plan holds a title, a
rationale, the study and its specs, a research priority that has nothing to do
with the scheduler's priority classes, a status set by hand (draft, ready,
closed or abandoned), an outcome, and an optional link to a preregistered
hypothesis. A submission is written by the CLI at submit time and records what
was sent: the template, image, priority class, specs and their hash, and who
sent it from where. It joins to run rows by workflow name. Neither table holds
a workflow phase or a run outcome. A plan's stage is derived from the rows
every time it's read: planned, submitted with no cell started, running, or ran,
which the app shows as "ran, needs a verdict".

The tracker's API is a FastAPI service, and its OpenAPI document is the
contract the web app's typed client is generated from, with a CI check for
drift. Reads go through a read-only database role, and plan edits go through
the experiment library's single writer. Nothing in the API submits, cancels or
re-runs. A workflow's live phase comes from Argo through a ten-second cache. A
404 shows as `gone` and any other failure as `unavailable`, never a 500. Since
early October, a workflow whose live object has been collected is read from
Argo's archive instead, so an old submission shows its final phase rather than
a blank.

The web app polls. The overview refreshes every fifteen seconds, and a running
run's detail every ten. There is no watch on Argo and no event feed. The
overview has a seven-day tally and a spike raster of the last fourteen days,
one row per study and one tick per run, coloured by outcome. The other views
are a plans board, submissions with their live Argo state, and runs with their
provenance, environment, failure detail, retry chain, metrics and artifacts.

The tracker can't show a cell's place in Kueue's queue. The portability rule
keeps Kueue out of the experiment repo, so all the tracker sees is `Pending`.
Queue and gang views belong to the platform side, and none exists yet.

**The card.** GPU telemetry comes from the host, because only the host sees
GPU processes from every container. Telegraf reads `nvidia-smi` every 15
seconds: utilization, memory, temperature, power, clocks and the PCIe link, and
memory per process. A script maps each process to its container through the
process's cgroup. Mapping a pod's cgroup to the pod's name needs a lookup in
the cluster, and the script runs unprivileged, so the privilege is split. A
root timer writes a map of pods every 30 seconds, and the unprivileged script
reads it. With every slice seeing all 16 GB, that per-process memory is the
only view of who is actually using the card. DCGM was ruled out: profiling
support on consumer Blackwell is unconfirmed, its exporter wants Docker with
`SYS_ADMIN` on a host that has no Docker, and DCGM has no per-process metrics
anyway. There are no SM or tensor-core counters.

**The cluster.** The OpenTelemetry collector sends cluster and kubelet
metrics, container logs and Kubernetes events to SigNoz. It scrapes Argo's
workflow controller, Kueue's controller over HTTPS with the collector's service
account token, and the vLLM pods by annotation. Volcano isn't scraped.

**Requests.** The vLLM servers emit a span per request. vLLM's token counters
attribute LoRA adapter traffic to the base model's name, so a thin reverse proxy
now sits in front of the 7B and emits a span per request carrying the adapter's
name. It also asks for usage figures on streaming requests that didn't. It
doesn't wake a model that's scaled to zero.

**Runs.** A run emits spans tagged with its id, under a resource that carries
the pod's name. The pod name is the join: the run row, the host's per-process
memory series and the spans all carry it. One smoke cell's memory, 374 MiB,
showed up in the host series under its pod name. Every emitter is best effort,
so a collector outage can't block a result from being written. Telemetry is
for operations only and is never read back as data.

These alerts go to one Discord channel:

| Alert                        | From                        | Fires on                                       | Fired in a drill |
| ---------------------------- | --------------------------- | ---------------------------------------------- | ---------------- |
| Argo workflow failed         | Argo's controller metrics   | a failed workflow in the last 5 minutes        | yes              |
| GPU step pending on Kueue    | Kueue's metrics             | an inadmissible workload for 15 minutes        | no               |
| Control-plane memory low     | node metrics                | under 15% of memory available                  | yes              |
| Kueue controller unavailable | Deployment metrics          | no available replica for 2 minutes             | yes              |
| GPU memory saturated         | host GPU metrics            | over 95% for 10 minutes                        | no               |
| GPU temperature              | host GPU metrics            | over 85 °C                                     | no               |
| Run failed                   | run rows, through Grafana   | a failed row in the last 10 minutes            | no               |
| Run stalled                  | run rows, through Grafana   | a running row silent for 2 h 15 min            | no               |

Kueue exports no metric for its webhook having no endpoints, so the controller
having no available replica stands in for it. The two run alerts are SQL over
the experiment database's read-only role, not rules over telemetry. A run
killed outright stops sending anything, and its row stays behind to be queried.

The first firing drill for the failed-workflow alert stayed silent. The rule
filtered on label names the series doesn't carry, and the right names were read
from Argo's source. Faking an outage was its own problem. Argo CD's self-heal
put back a `kubectl scale` to zero within about a minute, so the drills fake
one with a ResourceQuota of zero pods plus a pod delete.

## The Slurm cluster beside it

A small Slurm cluster runs alongside the Kubernetes stack, so that partitions,
QOS, job arrays, GPU resources and preemption by requeue are learned the Slurm
way as well. It is two unprivileged LXC containers on the GPU host: a
controller that runs the scheduler, the accounting daemon and a local MariaDB
and also takes jobs, and a compute node with the card mounted as one GPU.
Terraform builds them, and an Ansible playbook configures them.

Scheduling is backfill over consumable trackable resources. Preemption is by
QOS with requeue, on a ladder of `high`, `normal` and `low`, where high can
preempt both others and normal can preempt low. The batch partition sets
`OverSubscribe=NO`, so a low-priority job holding the cluster has to be
preempted to make room, which is what makes the drill meaningful. In the drill,
in mid-July, a low-QOS two-node job went in with requeue enabled, then a
high-QOS attacker. The attacker completed in 30 seconds, and the victim was
preempted, requeued and restarted from scratch, with one restart recorded. The
cluster has also run a job array across both nodes, a two-node Gloo all-reduce
between the containers, and a GPU job on the compute node.

Accounting is losable by design. The accounting daemon needs MySQL or MariaDB,
since Slurm dropped its Postgres plugin years ago, so a small MariaDB runs
inside the controller, and the playbook re-applies the cluster's registration,
QOS levels, accounts and associations idempotently. GPU jobs were missing from
accounting until the upgrade below turned that up. GPUs are now tracked as a
resource, so accounting reports GPU-seconds like any other.

In late September the cluster moved from Slurm 22.05 to 24.11, because 22.05's
REST plugins stopped at an old API version. That is four releases at once,
outside SchedMD's upgrade window, so the job history was dumped first and
accounting was recreated rather than migrated. The upgrade was done in place on
the containers. The REST daemon accepts JWTs only, and an unauthenticated call
gets a 401. The playbook generates the signing key once and never regenerates
it, which would invalidate every outstanding token. Minting a token stays a
manual step, since a token is a credential and not configuration.

The GPU partition was created down and has never been up. It stays down so a
Slurm GPU job can't land next to a language model on the card. The default
batch partition carries a QOS that refuses any GPU request at submit time, with the
error `QOSMaxGRESPerJob`, rather than leaving the job pending. A QOS does the job
because Slurm 24.11 has no partition-level way to deny GPUs. One gap remains. A
batch job that asks for no GPU at all can still open the card, because the
device files in the container are world-writable. Cgroup device control would
need an eBPF attach that an unprivileged container most likely can't make. That
hasn't been tried, because turning it on risks draining the node. The gap
closes when the card leaves the container.

In mid-September the plan was to extend these containers and keep Slurm off
Kubernetes. A week later the lab's goal was restated around patterns that
scale, and Slurm is now headed for Slinky, which runs it on Kubernetes so its
GPU jobs fall under the same Kueue quota as everything else. Its acceptance
test is a Slurm GPU job submitted while the 7B serves: it must either wait on
Kueue or preempt by priority class, and never share the card with the model.
Slinky isn't built.

## The training series

At the end of June the lab briefly had two GPUs: the 5060 Ti, and an older
Quadro P1000 (Pascal, 4 GB) in a laptop. A series of phases ran data-parallel
training across them, scheduled by Volcano, and measured it. The two cards need
different PyTorch builds, 2.8 for Blackwell and 2.4 for Pascal, and no NCCL
build spans both, so gradients moved over Gloo, a CPU collective, across the
gigabit LAN. From phase 20 the training loop ran its own all-reduce over Gloo,
flattening gradients to the CPU and weighting each rank by its batch size.

Each phase asked one question and chose what to measure to answer it:

| Phase | Question                                         | Measured                               | Result                     |
| ----- | ------------------------------------------------ | -------------------------------------- | -------------------------- |
| 13    | Does a gang place all or nothing?                | pods bound under contention            | neither pod bound          |
| 14    | Does DDP work across the two architectures?      | all-reduce result; compute ratio       | correct; 11.9× slower      |
| 16    | What does evicting a live gang cost?             | synced steps discarded                 | 24 of 24                   |
| 17    | Do checkpoints and a supervisor help?            | steps lost per preemption              | 4                          |
| 18    | Can the job train through the outage?            | steps trained alone; rejoin step       | about 220; step 271 of 600 |
| 19    | Where does a step's time go?                     | compute, waiting and network shares    | 7.3%, 89.4%, 3.4%          |
| 20    | Can batch sizing fix the straggler?              | waiting share; throughput              | 42.6% → 9.5%; 1.28×        |
| 21    | Does a smaller gradient help?                    | step time per gradient encoding        | fp16 1.41×                 |
| 22    | Can communication hide behind the backward pass? | exposed communication per step         | 141 → 41 ms                |
| 23    | How does utilization change with model size?     | compute MFU per card                   | 15.0 → 41.2%, 14.1 → 51.4% |

The models are small, 19 million parameters at most, and the numbers are
measurements on this pair of cards over a gigabit link.

**Preemption.** Volcano preempts only the slack above a gang's `minAvailable`,
so a gang at its minimum can't be preempted at all. A job with a lower minimum
can be, and phase 16 measured the cost for a job that wasn't built for it: 24
synced steps, all lost. Phase 17 added a restart supervisor and a checkpoint
every five steps, and the same event cost four steps. `torchrun` couldn't help
there. Its rendezvous fails across the two PyTorch versions, because 2.8 writes
timezone-aware datetimes and 2.4 compares timezone-naive ones. The phase used
plain `env://` rendezvous with a supervisor, and the job paused while its peer
was gone.

Phase 18 removed the pause. A membership controller of about forty lines, over
a long-lived TCPStore, let the job shrink to one worker and keep training. The
fast card trained alone for about 220 steps during the outage, the slow card
rejoined at step 271 with the current weights, and the job finished all 600
steps. That refuted an earlier note that this needed etcd or matching PyTorch
versions. The series' roadmap draws the conclusion that protecting a gang and
keeping it preemptible are mutually exclusive, so resilience has to live in the
job: checkpoints, a supervisor, dynamic membership.

**Where the time goes.** Phase 19 split a step into compute, waiting and
network, on a synthetic workload. A barrier before each all-reduce separated
waiting for the slow card from time on the wire.

<Figure num="Fig. 8" caption="Phase 19, the fast card's step: almost all of it spent waiting for the slow card. The network the series had suspected took 3.4%.">
  <StepTimeSvg />
</Figure>

The working assumption had been a jittery network link. iperf measured 919
Mbit/s over TCP, and a separate UDP run at 900 Mbit/s showed 0.01 ms of jitter
and no loss. The cost was the straggler: the P1000 computed about 13 times
longer than the 5060 Ti.

**Fixing the straggler.** Phase 20 moved to a real model, a
character-level GPT of about three million parameters with hand-written
attention, since
the Pascal build lacks PyTorch's fused attention. Splitting each batch by the
cards' measured speed, 58 and 6 instead of 32 and 32, cut the waiting from
42.6% to 9.5% of the step, a 1.28× speedup. That left the all-reduce at about
82% of the step. Phase 21 sent gradients in fp16, halving them from 12.8 to 6.4
MB, for 1.41×. Top-k sparsification with error feedback sent the fewest bytes,
and its CPU cost left it behind fp16, though it still beat fp32 at 1.15×.
Phase 22 overlapped the all-reduce with the backward pass, using hand-rolled
gradient buckets, in a more compute-bound setting.

<Figure num="Fig. 9" caption="Phase 22, all in one regime. fp16 gradients and overlap each give about 1.2×, and together 1.63×, because the fp16 all-reduce is smaller than the backward pass and overlap hides nearly all of it. Exposed communication fell from 141 ms to 41 ms per step.">
  <OverlapSpeedupSvg />
</Figure>

Phase 21's 1.41× and phase 22's 1.21× for fp16 come from different regimes and
don't combine. Phase 23 measured MFU against model size. Compute MFU rose with
size, from 15.0% to 41.2% on the 5060 Ti and from 14.1% to 51.4% on the P1000,
across 0.11 to 19 million parameters. MFU here is measured against each card's
fp32 CUDA-core peak. It measures utilization, and the P1000 posts the higher
figure while running about ten times slower per token. Phase 23's runs are
logged to MLflow.

The laptop has been offline since about July, so every two-GPU number above
comes from a node that can't currently rejoin, and the series hasn't been
re-run. On one node, the gang and preemption demos have been rebuilt and pass.

## What broke

<Incidents>
<Incident title="No GPU cell could run">

The first GPU cell submitted to the cluster failed, and no GPU cell could have
succeeded. The cell template's `when` conditions pasted the priority parameter
in unquoted. Every priority class name contains a hyphen, so `gpu-batch` was
parsed as the expression `gpu - batch`, and Argo failed with `Value 'gpu'
cannot be used with the modifier '-', it is not a number`. The only check
before that submit was a server-side dry run, which validates the schema and
never evaluates a `when`.

Pod-free probes on the live controller then ran all eight combinations of the
template's inputs. Four failed. Of the four that ran, one asked for a priority
class that doesn't exist, and the other three were CPU cells that got through
because `&&` short-circuited. No input could have produced a running GPU pod,
and a CPU cell with no priority failed too. The fix quoted both sides, a test
now holds the rule over every workflow file, and the resubmitted cell
succeeded. The postmortem's rules are to treat any value spliced into an
expression or a shell line as a quoting problem, and to count a dry run as a
schema check and nothing more.

</Incident>
<Incident title="Kueue's fail-closed webhook stopped pod creation">

Kueue's webhooks fail closed, which is correct: a GPU pod that skipped
admission would bypass the quota. In late September the control-plane VM ran
out of memory while Argo CD's application controller grew, and Kueue's
controller couldn't start against the struggling API server. With its webhook
down, no new pod could be created in any namespace Kueue manages for about
twenty minutes, the drill's own cleanup step included. The homelab writeup
covers the memory side.

The fix scoped Kueue's two pod webhooks to pods that carry a queue label. It is
a Kustomize overlay that renders the same chart and patches an
`objectSelector` onto both webhooks by name. Narrowing only the mutating one
would have left the validating one blocking every unlabelled pod. A second
Argo CD Application doing a server-side-apply patch was rejected, because Argo
CD uses one fixed field manager and the first Application's next sync would
erase the field. A Kyverno policy mutating admission objects was the other
rejected option. A drill then created an unlabelled pod while Kueue was down,
and saw a queue-labelled pod refused.

</Incident>
<Incident title="Kueue admitted pods the node then refused">

The first quota drills asked for several slices in one pod. Kueue admitted
those workloads, and every pod died within a second on the node with
`UnexpectedAdmissionError: maximum request size for shared resources is 1`. A
time-sliced card lets a pod hold at most one slice, and Kueue's quota check
doesn't know that. Every template now hard-codes one slice per pod, and
anything that needs more of the card runs as several one-slice pods, which is
also why fine-tuning reserves its quota with a ballast Job.

</Incident>
<Incident title="The model cache passed truncated downloads">

The Job that fills the model cache skipped any model whose `config.json`
already existed. A download that ran out of memory partway left that file
behind, so the check passed and the Job moved on. Neither cached model had
complete weights. One was missing one of its two weight shards, and the other
had none. The CI cache had the same bug, found the day before. The fill Job
now requires every shard listed in the model's index and no partial blobs, and
it has three times the memory.

</Incident>
<Incident title="A new GPU CI agent picked up builds it wasn't meant for">

A CI agent that runs build steps as pods in the cluster went in to give the
experiment repo a GPU test lane. Steps without an agent label can run on any
agent, so it started taking the experiment repo's ordinary CPU pipelines, and
Kyverno rejected those pods for missing resource requests or images from
unapproved registries. Any unlabelled step on the shared CI server could have
landed there the same way. The agent was scaled
to zero, and Argo CD's self-heal put it back at least twice. The fix gave the
CI namespace default resource requests and one narrow registry exception for
the CI's own git plugin, and the experiment repo's other pipelines were
labelled to stay on the Docker agent.

</Incident>
<Incident title="Argo CD's self-heal undid manual fixes">

Self-heal applies what git says, which includes undoing what an operator just
did. It reverted a `kubectl scale` to zero within about a minute during an
alert drill, and did it at least twice more while the CI agent above was being
paused. It also kept a failing
Job alive. A cache fill for a gated model failed on a 403, the Job's time to
live deleted it every ten minutes, and self-heal recreated it each time. The
model came out of the fill list until its licence was accepted. Drills now fake
outages with a ResourceQuota of zero pods, which self-heal leaves alone.

</Incident>
<Incident title="Image pushes failed at sixty seconds, then at thirty minutes">

The first pushes of the 4.4 GB lab image to the registry failed when Traefik's
60-second read timeout cut long blob uploads. Splitting the Python environment
into eight smaller layers didn't help, because buildx uploads layers in
parallel and each upload still ran past the limit. The timeout went up to 30
minutes. Later, pushes that ran 30.1 to 30.5 minutes failed the same way, so it
went to 45 minutes, a value picked over longer ones to limit exposure to
slow-client attacks.

</Incident>
<Incident title="A dead node wedged the device plugin">

Turning on time-slicing wedged the device plugin's rollout. The DaemonSet
allows one unavailable pod, and that allowance was held by a pod stuck
terminating on the offline P1000 node, which had been NotReady for 88 days and
would never confirm the deletion. A taint couldn't help, because those
DaemonSets tolerate every taint. A forced delete of the pod cleared the wedge.
The same trap was armed in three other DaemonSets, and the dead Node object was
deleted the same day.

</Incident>
<Incident title="Draining the GPU node can't fully succeed">

In early October the GPU node was drained for real, with a GPU Job running.
The Job's pod was evicted, its replacement ran, and the Job completed. The
resident models were Ready within a second of uncordon, warm from cached
weights. `kubectl drain` itself exited 1, and always will on this cluster: the
registry runs one replica on one node behind a disruption budget that requires
one, so it can never be evicted. The drain also briefly left Kueue's webhook
with no endpoints.

</Incident>
<Incident title="Slurm's REST daemon looked started and wasn't">

After the upgrade, Ansible reported the REST daemon started, and it had exited
30 ms later. It was binding a unix socket after dropping privileges and failing.
The fix runs it on TCP only and adds a liveness check that waits for the port,
so a daemon that dies right after starting fails the play.

</Incident>
<Incident title="A schema accepted what Kueue's webhook refused">

One cohort setting passed the CRD's schema and was refused only by Kueue's
webhook at the first sync: borrowing within the cohort requires reclaiming
within it too. The CRD's schema doesn't encode that rule, and Kueue wasn't
installed yet, so the schema was the only check available beforehand.

</Incident>
</Incidents>

## What isn't done

The lab has one consumer GPU, a gigabit LAN, small models and no external
users. Within that:

- **No real study has run on the cluster.** Every run recorded there is a
  platform smoke test or drill. The sweep template has only been dry-run, and a
  live checkpoint resume hasn't been run.
- **Run events aren't published.** The outbox and the Argo Events consumer are
  a design slot, nothing alerts on an interrupted run that was never retried,
  and Argo CD sends no notifications.
- **The GPU test lane fails on credentials.** It runs on the card and fails
  with a 401 fetching a gated model, until two CI settings allow the cache
  volume and the token. There are no evaluation gates.
- **Several alerts haven't fired.** The pending-GPU alert, the GPU memory and
  temperature alerts, and the two run alerts have never been fire-tested.
- **VRAM accounting is wired and inert.** Every tenant declares zero, and DRA,
  the real target, is alpha everywhere it would need to run.
- **Slinky isn't built**, the Slurm GPU partition is down, and a batch job that
  asks for no GPU can still reach the card.
- **The lease is still installed**, and the card is still mounted into the
  tower's other containers.
- **The two-GPU training series hasn't been re-run**, and the laptop it needs
  is offline.

## What runs on it next

The first experiments are systems measurements on the card itself: serving
characterization, the cost of sharing one card, a request's path into GPU time,
and an evaluation gate for promoting a model. Each study opens with a
calibration milestone, such as an in-process GPU sampler checked against
`nvidia-smi`, and each ends in a writeup with raw data someone else can re-run.
